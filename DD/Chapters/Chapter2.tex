In this section of the document we will be focusing on the whole deployment of BBP and the motivations behind our choices.

We divided our system into three main tiers: presentation, application and data tiers (better explained in Section~\ref{subsec:three-tier}) to better isolate common features between all tangible and intangible instances of all the objects we used. Below, a list of all the actors and objects involved:
\begin{itemize}
	\item \textbf{Personal Device}: a personal device consists of a Sensor device (here modeled as the union of all the device's movement sensors) and an OS that can be either Android or iOS. It is to be intended as a personal piece of hardware such as a smartphone or smartwatch that is carried by the user throughout the execution of the application. The personal device communicates with the Application Server using a local view instance of the app, here called Application: every request made by the Application to the Application Server follows a RESTful interaction style over HTTPS.
	\item \textbf{API Gateway}: it's a node offered by a third party (such as AWS or Google Cloud Services) that has a built-in WAF and load balancer to better distribute traffic to all the distributed Application Servers avoiding single points of failure. 
	\item \textbf{Application Server}: it's a device that contains the logic of the application and connects together all the drivers needed to the application to work. It is connected with external APIs using REST and with multiple databases using a continuously working connection pool.
	\item \textbf{Database}: we decided to have different databases (one main database, more replicas used only in read mode) with a connection pool contained inside the Application Server, so that databases are actually protected by a limited amount of opened connection and overload is not possible. This feature is extremely useful to minimize concurrency problems and the number of connections can be adjusted accordingly to the number of requests seen to have the optimal balance of hardware usage and system efficiency: we chose Linux as the OS because of its open source roots and MySQL for its robustness.
\end{itemize}
Now for a closer look at some of the components of the devices themselves:
\begin{itemize}
	\item \textbf{Application Artifact}: the client side application. It is used primary as the presentation layer and stores a signed JWT (JSON Web Token) used for authentication: it is connected with all sensors needed to detect movements in automated mode using cross-platform mobile frameworks.
	\item \textbf{BBP Server App}: the actual model of our application. Here, the logic of the app is stored and ensures all operations are coherent with user requests following the MVC pattern: it is the recipient of all the managers and connects them to every driver needed to interface to external tools.
\end{itemize}

\section{Styles and Patterns}
\label{subsec:three-tier}	%da lasciare per link
BBP will be developed using the client-server paradigm integrated with a three-tier architecture and the model-view-controller pattern: the aim of this mixed architecture is to achieve a clear separation between all the roles of the devices that are used and to better control each one of them. The tiers that are involved are:
\begin{itemize}
	\item \textbf{The Presentation Tier} - This tier serves as the view component of the application and contains the software that needs to work strictly with the user's hardware (in our case, the personal device and the sensors connected to it): it can be seen as the top-level tier and it aims to be stateless, though some information about the user is saved by using JWT tokens for authentication. It's main functionality is to display all the informations and useful actions the user can do with the application itself and show all the outputs sent by the backend of the system, it does not contain the whole logic to prevent the user to change it locally and perform unauthorized actions: this also makes the application lighter in memory usage terms. To be able to actually make a platform-independent application compatible with the major operative systems we opted to use Flutter libraries in order to use a common language between OS in retrieving the sensors' informations.
	\item \textbf{The Application Tier} - This tier serves as the core logic component of the application and it is composed by the application servers, it is where all the user actions are checked and, if contextually correct with the state of the machine, validated and executed: it can be seen as a middle-level tier and as the space where all the data retrieved in the lower level are computed and then sent to the user in form of useful informations. We opted to have multiple application servers since with the use of an API Gateway (explained further) with a load balancer inside it is possible to do routing to specific servers, meaning that the same user will use the same server having the JWT as its id: this way, scaling is modular and possible and if a failure inside a server is detected it is possible to re-route the user to a different server avoiding downtime.
	\item \textbf{The Data Tier} - This tier serves as the main source of user and application data gathered inside databases: we opted to have a main database with a connection pool (so that the number of connections can actually be regulated granting flexibility and avoiding overloading) and several secondary databases used for read only operations, updated after write actions inside the main database. This achitecture avoids downtime of the data tier if the main database breaks (one of the secondary databases becomes the new main database) and at the same time avoids having cloned information issues (more than a main database can be difficult to handle by dealing with synchronization issues).
\end{itemize}
In addition to those three tiers, we opted to insert a third party API Gateway that connects the presentation tier to the application tier. To fully satisfy scalability and security concerns, this API Gateway must have a load balancer (to evenly distribute clients connections between all servers) and a WAF (to protect attacks using a protection firewall): AWS and Google Cloud Services are some examples of third part companies that offer this kind of service.

As anticipated before the whole architecture can be seen as a client-server interaction, where all actions are event-driven: the client is the active part of almost all transactions (apart from notifications made by the server, like the starting of the automated mode recording) but is always checked by the logic inside the server, so that eventually communication errors or intentional attacks made by bad users are intercepted. Being the communication handled with REST it's easy to encode error messages and to use HTTPS to understand everything that is happening, both in front-end and back-end scenarios.
