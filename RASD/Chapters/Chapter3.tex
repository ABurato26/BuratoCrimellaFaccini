\section{Performance Requirements}
The system relies heavily on real-time data acquisition, geospatial processing, and user interaction through 
mobile devices. Therefore, specific performance constraints must be met to ensure a proper user experience and the 
integrity of the collected data.

\begin{itemize}
    \item \textbf{Response Time and Latency:}  The system must ensure low latency during critical user interactions to maintain usability. Specifically, for general browsing and viewing of bike paths, the system should render map visualizations and path details within 3 seconds of a user's request, assuming a standard 4G/5G connection. For the route-finding feature, the algorithm computing the path score and optimal route must complete execution within 5 seconds. Regarding the "Automated mode," the system is required to process sensor inputs (accelerometer and gyroscope) and GPS data in real-time. The lag between the physical detection of an obstacle and its internal logging on the device should be very reduced to ensure accurate timestamping and location tagging. However, the complex merging of data from the same path can be performed asynchronously on the server side, provided that the updated status becomes available to the community within a reasonable timeframe like 5 minutes of data upload
    \item \textbf{Number of Concurrent Users:} As a community-driven platform managed by a biker's association, BBP must support a significant number of concurrent users, particularly during periods where the numbers of bikers could increase a lot, such as weekends and holidays. The system backend must be capable of handling at least 1,000 concurrent active sessions without performance degradation
    \item \textbf{Data Storage and Capacity:} The storage infrastructure must be designed to accommodate high-volume geospatial and time-series data. Since the application records continuous GPS tracks, along with high-frequency accelerometer and gyroscope readings for obstacle detection, the database will grow rapidly. The system requires a scalable storage solution capable of archiving historical trip data while keeping active path inventories and recent statistics immediately accessible. Provisioning should be made for storing several Terabytes of data over the first few years of operation, with a strategy for data retention that prioritizes the freshness of path conditions
    \item \textbf{Network Bandwidth and Connectivity:} The system must be resilient to variable network conditions. The application should optimize data transmission to minimize bandwidth usage, which is crucial for users with limited data plans. In "Automated mode," the system must implement a "store-and-forward" mechanism: if the user enters an area with poor or no connectivity, the application must locally buffer all GPS and sensor data. Once connectivity is restored, the system should upload the accumulated data without freezing the user interface or interrupting the ongoing recording of the trip. The transmission of external meteorological data should be lightweight, fetching updates only at necessary intervals rather than continuously streaming, to preserve bandwidth
    \item \textbf{Energy Efficiency:} A critical performance requirement for the system's component is battery consumption. The simultaneous usage of the GPS module, accelerometer, gyroscope, and background processing algorithms constitutes a high energy drain. The application must be optimized to ensure that running the "Automated mode" doesn't reduce a standard smartphone battery excessively fast. The optimal target should be to allow a user to track a continuous ride of at least 5 to 8 hours on a fully charged device

\end{itemize}

\section{Design Constraints}
The design and development of the Best Bike Paths (BBP) system must adhere to specific boundaries imposed 
by the operational environment, regulatory requirements, and the technological limitations of the end-user devices.
These constraints influence the architectural decisions and the selection of technologies to ensure the system is robust, 
legal, and usable.

\subsection{Standard compliance}
Given the nature of the application, which involves the collection, storage, and processing of user data and geolocation tracking,
the system must strictly comply with relevant data protection regulations. Specifically, since the application tracks users' movements 
and associate trips with registered profiles, adherence to EU's GDPR (General Data Protection Regulation) is mandatory.
Moreover, the system relies on external services. Therefore, it must comply with standard geospatial data formats to ensuring interoperability 
with standard mapping APIs and the navigation modules. The communication between the mobile application, the backend server, and the external 
meteorological service must adhere to modern security standards, necessitating the use of HTTPS and TLS protocols to encrypt data in transit. 
Finally, the integration of weather data implies compliance with the specific API standards provided by the chosen third-party meteorological service provider.

\subsection{Hardware limitations}
The "Automated mode" of the BBP application introduces significant hardware dependencies that act as constraints on the system's 
availability and performance. The primary limitation is the dependence on specific mobile sensors. For the application to function user's mobile device 
must be equipped with a high-precision GPS receiver, an accelerometer, and a gyroscope. Additionally, the continuous usage of these sensors imposes a constraint 
regarding battery consumption. The design must optimize sensor polling rates to prevent excessive battery drainage, which would negatively impact the user experience 
during long bike trips. Finally, the system is constrained by network connectivity hardware. While the application collects data locally, the features related to 
retrieving meteorological information, publishing path data, and merging crowd-sourced information require an active internet connection. The system design must, 
therefore, account for intermittent connectivity scenarios, typical of outdoor cycling routes, by implementing local caching mechanisms until a stable connection is re-established.
